# 把 Markdown 交还给写作者：ACKS Markdown Editor 是怎么诞生的

![ACKS Markdown Editor：从 Markdown 到可发布文章](asset:img-cover)

如果你已经习惯用 Markdown 写作，大概经历过这种时刻：

文章在笔记软件里明明**结构清楚、重点明确、代码和列表都很规整**，复制进公众号后台以后，标题变了、间距乱了、代码块塌了，图片和表格还要重新整理。

> 每次发布都像重新排一遍文章。写作已经结束，格式劳动才刚刚开始。

公众号自带的是一套常规富文本编辑器。它当然能完成基本排版，但它对 Markdown 和已经组织好的 HTML 并不友好。对于习惯 `Markdown → 版本管理 → 多端复用` 工作流的写作者来说，最难受的不是少一个按钮，而是**原本稳定的写作链路被打断了**。

ACKS Markdown Editor 就从这个很具体的问题开始。

---

## 01｜它不是为了替代写作，而是为了减少发布前的返工

项目最早只是一个本地单文件原型：能写 Markdown，能看成稿，能复制一份尽量稳定的 HTML。

但真正开始使用之后，问题很快暴露出来：

1. 熟悉 Markdown 的人需要完整源码，不熟悉的人需要可发现的格式工具；
2. 图片如果直接写成 Base64，源码会被一长串编码淹没；
3. 主题不应该只是换颜色，更不能让十几个主题复用同一套装饰；
4. DOCX、TXT 和外部 Markdown 文稿需要先预览、再导入，不能悄悄丢格式；
5. 两个标签页同时打开时，旧稿不能覆盖新稿；
6. 导出的 ZIP 必须真的带走表格和引用里的图片。

于是，我们给自己定了一个不太保守的前提：**允许推翻重做，只保留真正有价值的工作流。**

经过几轮审计和整改，它逐渐变成了现在的样子：

- 三种工作模式；
- 43 款文章主题与 9 个排版配方；
- 完整格式工具和块级编辑；
- MD / TXT / DOCX / ACKS 文档导入；
- 本地历史、冲突保护和资源完整性检查；
- 公众号 HTML、完整 JSON、Markdown 图片包输出；
- 单文件、Docker、HTTPS 三种使用与部署形态。

<mark>它仍然是一个轻量工具，但不再是一个只能演示的 Demo。</mark>

## 02｜三种模式，分别服务三个阶段

| 模式 | 适合做什么 | 设计重点 |
| --- | --- | --- |
| 写作 | 逐段组织内容、使用格式工具 | 少打断、容易发现、保留 Markdown |
| 源码 | 精确编辑整篇 Markdown | 不藏语法、不回写混乱 HTML |
| 成稿 | 检查主题、排版与公众号输出 | 以最终阅读效果为准 |

### 写作模式

点击任意段落即可编辑该 Markdown 块。常用工具栏提供粗体、斜体、标题、列表、链接和图片；完整工具面板还包括：

- H1–H4 标题；
- 有序、无序和任务列表；
- 引用、代码块、表格向导；
- 删除线、下划线、高亮；
- 字体、字号、颜色、波浪线和重点号。

### 源码模式

源码永远是完整 Markdown。插入图片后，看到的是：

```md
![一张图片](asset:img-001)
```

图片本体放在文档资源表里，导出时再写入 ZIP。这样既不会让源码被 Base64 淹没，也不会把图片和正文拆散。

### 成稿模式

成稿区分为“完整效果”和“公众号输出”：

- **完整效果**保留文章主题的全部表现；
- **公众号输出**把样式转成可复制的内联 HTML，并明确提示哪些图片需要重新上传。

这两个视图不假装完全一样，因为公众号后台会继续清洗 HTML。真实发布前，仍然应该做最后一次检查。

## 03｜主题不是皮肤，而是一套阅读秩序

最初的主题数量不少，但复用率也很高：相似的笔刷、色块和标题容器反复出现。后来我们重新给每个主题建立自己的视觉元素。

例如：

- 留白禅意使用**枯山水砂纹与置石**；
- 宋式·雅使用**青瓷小瓶与疏梅**；
- 先锋国潮使用**朱砂云雷回纹**；
- 技术文档使用**协议分支电路**；
- AI 报告使用**推理节点菱网**；
- 欧式古典使用**莨苕卷叶**。

现在的主题库包含 19 款 ACKS 主题和 24 个明暗版本，共 32 组视觉家族。明暗版可以保留家族关系，不同主题之间则尽量不再共用同一张素材。

这一段也顺便展示几种受限格式：<u>下划线</u>、~~删除线~~、<span data-md-color="#B33A1B">自定义强调色</span>、<span data-md-decoration="wavy">波浪线</span>、<span data-md-decoration="dots">重点号</span>，以及[一段链接样式](#)。

这些格式会经过白名单校验，不开放任意 HTML 或 CSS。

## 04｜从输入到发布，核心链路是什么

![ACKS Markdown Editor 架构与发布链路](asset:img-workflow)

整个应用没有传统后端数据库。核心数据模型可以简化为：

```js
{
  source: "完整 Markdown",
  assets: { "img-001": "图片资源" },
  themeSnapshot: { /* 主题快照 */ },
  recipeId: "default",
  overrides: { /* 字号、行距等微调 */ }
}
```

渲染链路则是：

```text
Markdown
  → Marked 语法解析
  → DOMPurify 安全清洗
  → 主题与配方渲染
  → 完整效果 / 公众号 HTML / JSON / ZIP
```

### 技术栈

| 层级 | 技术 |
| --- | --- |
| 编辑器界面 | HTML5、CSS、Vanilla JavaScript |
| Markdown | Marked 18 |
| 安全清洗 | DOMPurify 3 |
| DOCX 导入 | Mammoth 1.12 |
| ZIP 与图片包 | fflate 0.8 |
| 图标 | Phosphor Icons |
| 本地保存 | LocalStorage、Web Locks、文档历史 |
| 构建 | Python 3，生成单文件 HTML |
| 容器 | Nginx Unprivileged、Docker Compose |
| 反向代理 | Caddy、Cloudflare |

这里有一个重要选择：**核心依赖、图标、主题和素材都被构建进单个 HTML 文件，不依赖运行时 CDN。**

用户主动引用的远程图片仍可能联网；可选的主题生成模型只发送用户填写的主题描述，API Key 不会写入本地存储。

## 05｜DOCX 能保留多少

DOCX 导入不是把 Word 页面截图塞进编辑器，而是把内容转换成可继续编辑的 Markdown。

已重点处理的内容包括：

- 标题、段落；
- 粗体、斜体、下划线、删除线；
- 上标、下标；
- 有序、无序列表；
- 安全链接；
- 普通表格和合并单元格；
- 正文与表格中的常见图片；
- 可选保留显式文字颜色、字号和字体类别。

无法一比一复刻的部分，也会在确认导入前列出：

- 页眉、页脚、页码；
- 分页、分栏、纸张和页边距；
- 浮动图片与文本框位置；
- 精确字体、复杂继承样式；
- 复杂公式、图表和嵌入对象。

> 导入成功，不应该等于“什么都没说，然后悄悄丢掉一部分内容”。

所以流程被设计成：**选择文件 → 本机转换 → 查看预览与提示 → 选择替换或追加 → 确认导入。**

## 06｜本地保存为什么也需要冲突保护

如果两个标签页同时打开同一篇稿件，最简单的 `localStorage.setItem()` 会形成“最后写入者获胜”。旧标签页可能把新内容直接覆盖掉，而且用户毫无感知。

现在，保存会在 Web Lock 内检查文档版本：

- 当前版本一致，才允许写入；
- 发现其他标签页已经更新，立即暂停自动保存；
- 本窗口内容保存为冲突恢复副本；
- 用户可以下载本窗口稿件，或备份后载入较新版本。

这也是为什么生产环境推荐使用 HTTPS 或 localhost，而不是直接双击 `file://`。

### 发布前检查清单

- [x] Markdown 和主题渲染通过测试
- [x] 图片 ZIP 往返不丢资源
- [x] 多标签页不会静默覆盖
- [x] Docker 非 root、只读根目录
- [x] HTTPS、健康检查、安全头
- [ ] 公众号后台粘贴后人工检查
- [ ] 真实 iPhone 输入法与文件选择检查

最后两项没有被测试报告冒充成“已经完成”。

## 07｜如何使用

1. 在写作模式组织内容；
2. 需要精确控制时切到源码；
3. 插入图片、表格、引用和代码；
4. 在成稿里选择文章主题与配方；
5. 查看公众号输出；
6. 复制到公众号后台，重新上传图片并检查最终效果；
7. 发布前下载一份完整 JSON 备份。

**一个很实用的习惯：**重大导入、切换浏览器、调整大量主题设置之前，先点“下载完整文档”。

## 08｜如何部署

### 最简单的本地启动

```bash
python3 -m http.server 8080 --bind 127.0.0.1
```

然后在浏览器访问本机 `8080` 端口。

### Docker Compose

```bash
cp deploy/deployment.env.example deployment.env

# 填写 VERSION、VCS_REF 和 IMAGE_TAG

docker compose \
  --project-name acks-markdown-editor \
  --env-file deployment.env \
  -f deploy/compose.production.yml \
  up -d --build
```

容器默认只绑定回环端口：

```text
127.0.0.1:5703 → Nginx:8080
```

再由 Caddy 提供域名、HTTPS、压缩和安全响应头。

### 当前生产形态

```text
Cloudflare
  → Caddy（80 / 443）
  → 127.0.0.1:5703
  → 非 root Nginx 容器
  → 单文件 ACKS Markdown Editor
```

容器使用只读根目录、移除全部 Linux capabilities，并开启 `no-new-privileges`。

## 10｜写在最后

我想做的不是再造一个“功能更多的富文本编辑器”，而是把一条已经很成熟的 Markdown 写作链路，稳稳地接到公众号发布之前。

写作时，工具退后。

发布时，结构、图片、主题和备份都还在。

<mark>如果 ACKS Markdown Editor 能让一篇文章少返工十分钟，它就已经完成了最重要的任务。</mark>

这篇文章本身就是新的内置示例：它同时使用了标题、表格、引用、任务列表、代码、图片、链接和扩展文字格式。以后打开编辑器，不只会看到一个功能列表，而会看到这个工具为什么存在。
